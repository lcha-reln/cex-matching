# M06 market operating mode and deterministic Mass Cancel contract

`course/m06-start` freezes the **READY / GOAL_NOT_IMPLEMENTED** boundary on top of
`course/m05-complete`; `course/m06-complete` is the later **CODE_VERIFIED / PASS** target described
by this contract. M06 adds one complexity dimension only: an explicit per-instrument operating mode
governs customer actions, and an operator may terminate the complete resting book in one
deterministic command after the market has reached `HALTED`.

M06 does not add STP, persistence, a management console, authorization lookup, networking, Aeron,
or a second instrument. A mode transition is not an implicit clear-book switch. Halting and Mass
Cancel are separate commands, separate results, and separate serialized application boundaries.

## Inherited boundary

- The only instrument remains `BTC-USDT`; every order is still a price-protected limit order.
- M00 field validation, M01 price-time priority, M02 irreversible lifecycle, M03 independent-model
  proof, M04 execution policies, and M05 versioned order-entry rules remain authoritative.
- Existing `place`, `placeRequest`, `placeGoverned`, `cancel`, Prepare, Activate, and snapshot
  entrypoints remain callable.
- M05 rule version `0` remains the bootstrap identity. Mode does not rewrite rule artifacts,
  admission attribution, accepted sequence, or historical evidence.
- Calls remain caller-serialized. `matching-core` still owns no thread, clock, random source, file,
  network, database, or Aeron dependency.
- M06 is an evidence-only course unit and creates no `matching-*` product release.

The root build remains gated by the completed M05 proof. The M06 start check verifies only this
course declaration and the frozen M06 inputs; it does not claim that the M06 implementation,
reference model, generated judge, mutants, or evidence already exist.

## One operating-mode axis

The engine bootstraps in `OPEN` with mode revision `0` and no transition or Mass Cancel fence:

```text
enum MarketMode {
  OPEN,
  CANCEL_ONLY,
  HALTED
}
```

The permission matrix is exact:

| Action | OPEN | CANCEL_ONLY | HALTED |
| --- | --- | --- | --- |
| Customer Place | allowed | `MARKET_NOT_OPEN` | `MARKET_NOT_OPEN` |
| Customer Cancel | allowed | allowed | `MARKET_NOT_CANCELABLE` |
| Prepare/Activate rule set | allowed | allowed | allowed |
| Change operating mode | transition graph | transition graph | transition graph |
| Operator Mass Cancel | `MARKET_NOT_HALTED` | `MARKET_NOT_HALTED` | allowed |
| Read detached snapshots | allowed | allowed | allowed |

`CANCEL_ONLY` drains customer orders without admitting new ones. `HALTED` rejects both customer
Place and customer Cancel so that only the explicit operator Mass Cancel can mutate the book.
Prepare and Activate remain deterministic matcher commands in every mode; they never act as a
node-local refresh and never clear the book.

## Operator boundary

The new command values and entrypoints are:

```text
OperatorId(String value)

ChangeMarketMode(
  ApplicationSequence expectedApplicationSequence,
  MarketMode expectedMode,
  MarketMode targetMode,
  OperatorId operatorId
)

MassCancel(
  ApplicationSequence expectedApplicationSequence,
  MarketMode expectedMode,
  OperatorId operatorId
)

MarketControlBatch changeMarketMode(ChangeMarketMode command)
MassCancelBatch massCancel(MassCancel command)
```

`OperatorId` is stable audit attribution for a caller that an upstream control plane has already
authorized. It is not a credential, role, signature, or permission proof. `matching-core` never
queries an IAM service and never infers authorization from the string. The value must contain one
to 128 non-blank characters and is copied unchanged into successful and rejected control events.

Authorization, dual control, approval workflow, operator UI, audit-log storage, and revocation are
outside M06. The explicit command boundary makes those systems possible without pretending they
are already implemented.

## Safe transition graph

The only successful transitions are:

```text
OPEN        -> CANCEL_ONLY
OPEN        -> HALTED
CANCEL_ONLY -> OPEN
CANCEL_ONLY -> HALTED
HALTED      -> CANCEL_ONLY
```

`HALTED -> OPEN` is rejected as `INVALID_TRANSITION`; a safe reopen must pass through
`CANCEL_ONLY`. A request whose target equals the observed mode is rejected as `NO_MODE_CHANGE`, not
accepted as an idempotent success. This keeps every successful transition meaningful and prevents
an operator retry from hiding whether a different command already changed the mode.

Change evaluates these checks in exact order:

```text
EXPECTED_APPLICATION_SEQUENCE
-> EXPECTED_MODE
-> NO_MODE_CHANGE
-> ALLOWED_TRANSITION
-> MODE_REVISION_CAPACITY
-> APPLY_TRANSITION
```

The stable rejection codes are:

```text
APPLICATION_SEQUENCE_MISMATCH
EXPECTED_MODE_MISMATCH
NO_MODE_CHANGE
INVALID_TRANSITION
```

Every deterministic success or rejection consumes exactly one `ApplicationSequence`, just like
M05 control commands. Null/schema construction failure and `SYSTEM_ERROR` consume none. A failed
request preserves mode, mode revision, rule state, book, lifecycle registry, accepted sequence,
last transition fence, and last Mass Cancel fence. It must never reset the mode to `OPEN`.

A successful transition increments `modeRevision` exactly once and retains:

```text
ModeTransitionFence(
  appliedCommandSequence,
  modeRevision,
  previousMode,
  activeMode,
  nextAcceptanceSequence
)
```

It changes no order quantity, priority, lifecycle, rule identity, prepared slot, or rule-control
revision. In particular, `OPEN -> HALTED` does not scan or clear the book.

## Customer decision priority

Place preserves the M05 prefix and inserts mode permission only after the venue entry rule, but
before FOK/Post-only reads the book:

```text
M00_FIELD_VALIDATION
-> EXECUTION_POLICY_VALIDATION
-> DUPLICATE_ORDER_ID
-> EXPECTED_ACTIVE_RULE_SET
-> ACTIVE_ORDER_ENTRY_PRICE_BAND
-> MARKET_MODE_PERMISSION
-> POLICY_STATE_PRECHECK
-> ACCEPTANCE_SEQUENCE_CAPACITY
-> ACCEPT_AND_EXECUTE
```

Therefore malformed, duplicate, stale-rule, or out-of-band input retains its historical result.
A valid otherwise-admissible Place in `CANCEL_ONLY` or `HALTED` returns singleton
`PlaceRejected(MARKET_NOT_OPEN)` before FOK/Post-only liquidity inspection, accepted-sequence
allocation, identity reservation, or maker mutation.

Cancel freezes a different order because a halt must hide order lifecycle from customer mutation:

```text
FIELD_VALIDATION
-> MARKET_MODE_PERMISSION
-> ORDER_LOOKUP_AND_LIFECYCLE
-> CANCEL
```

Consequently, any schema-valid customer Cancel in `HALTED` returns
`CancelRejected(MARKET_NOT_CANCELABLE)` even when the order ID is unseen, filled, or already
canceled. In `OPEN` and `CANCEL_ONLY`, the M02 lookup and terminal rejection semantics remain
unchanged.

## HALTED-only Mass Cancel

Mass Cancel evaluates and freezes all failure conditions before touching the first order:

```text
EXPECTED_APPLICATION_SEQUENCE
-> EXPECTED_MODE
-> REQUIRE_HALTED
-> FREEZE_GLOBAL_ACCEPTANCE_ORDER
-> RESULT_AND_SEQUENCE_CAPACITY
-> ATOMIC_TERMINATION
```

The stable rejection codes are:

```text
APPLICATION_SEQUENCE_MISMATCH
EXPECTED_MODE_MISMATCH
MARKET_NOT_HALTED
```

A rejection is one `MassCancelEvent.Rejected` and leaves mode, both revisions, rules, fences, book,
registry, quantities, and accepted sequence unchanged. It still consumes its application boundary.
The implementation may not begin deleting orders and then discover a stale fence, wrong mode,
sequence overflow, or result-capacity failure.

In `HALTED`, the command snapshots every positive RESTING remainder and sorts the frozen set by
global ascending `AcceptanceSequence`. It does not traverse price levels, bid/ask maps, hash-map
iteration order, or current best price to define output order. Side and price affect neither the
sequence nor membership. Each frozen order is terminated exactly once, retains its order ID, and
becomes irreversibly `CANCELED`.

The successful event grammar is:

```text
MassCancelEvent.Started(
  applicationSequence,
  operatorId,
  HALTED,
  modeRevision,
  restingOrderCount
)

MassCancelEvent.OrderCanceled(...) * restingOrderCount

MassCancelEvent.Completed(
  applicationSequence,
  operatorId,
  HALTED,
  modeRevision,
  canceledOrderCount
)
```

Every `OrderCanceled` carries the original acceptance sequence, order ID, side, price, exact
positive canceled remainder, admission `RuleSetIdentity`, and current execution
`RuleSetIdentity`. The application sequence and operator ID are identical across the complete
batch. An empty halted book is a successful two-event `Started -> Completed` batch with count zero.

Successful Mass Cancel:

- consumes one application sequence regardless of order count;
- does not consume or rewind acceptance sequence;
- remains in `HALTED` and does not increment mode revision;
- does not alter active/prepared rule sets, rule-control revision, or activation fence;
- records a `MassCancelFence` with application sequence, mode revision, operator, count, and empty
  or exact first/last canceled acceptance-sequence bounds;
- returns an empty detached book;
- retains every canceled identity in the lifecycle registry, so a later valid Cancel reports
  `ORDER_ALREADY_CANCELED` and reusing the order ID remains `DUPLICATE_ORDER_ID`.

The event list, book mutation, lifecycle updates, and retained fence form one atomic command result.
There is no partial-success status and no implicit fallback to `OPEN`.

## Rule-set interaction

Mode and M05 rule lifecycle are orthogonal serialized state machines:

- Prepare/Activate are legal in every mode and retain their M05 expected-active and application
  fences.
- A mode change does not activate, discard, or recompute a prepared artifact.
- Rule activation never changes market mode or clears existing orders.
- Mass Cancel does not change active/prepared rule state.
- Every canceled order preserves the rule identity under which it was admitted, while the batch
  also identifies the active rule under which termination executed.

This contract lets an operator halt, prepare/activate a new entry rule, terminate grandfathered
orders explicitly, inspect evidence, move to `CANCEL_ONLY`, and finally reopen. M06 does not bundle
those commands into an implicit “update rule and clear” operation.

The corpus covers bootstrap compatibility, the complete customer permission matrix, safe reopen,

empty success, bid-only, ask-only, cross-side/cross-price global order, terminal identity, and rule

- a third event/state ledger must derive mode, mode revision, fences, lifecycle, rule attribution,

Completion freezes real M06 fixed and generated histories only after the implementation produces

## Start, completion, evidence, and stopping point

At `course/m06-start`:

```bash
./gradlew clean build --no-daemon
./gradlew m06Check --no-daemon
```

The clean build proves M05 remains the completed baseline. `m06Check` validates `course.properties`,
the strict scenario/generator schemas, both frozen input hashes, the 15/64 corpus, seed `6606`,
160-by-64 profile, five lanes, 26 coverage IDs, ten mutant IDs, and five tutorial permalinks. It
writes strict `matching.m06.check.v1`, reports `GOAL_NOT_IMPLEMENTED`, and exits non-zero
intentionally.

At `course/m06-complete`, the completion check may report PASS only after production, independent
reference, third ledger, fixed/generated differential comparison, coverage witnesses, ten
one-minimal mutant counterexamples, strict replay, architecture checks, and all inherited semantic
regressions pass. Clean annotated-tag evidence records real hashes and limitations with
`productRelease: null`.

M06 excludes STP and participant identity, WAL and durable idempotency, Snapshot, protocol,
networking, database state, operator authentication/authorization, management UI, performance,
Aeron, replication, failover, multiple instruments, automatic reopening, and implicit rule-driven
book clearing.

The M06 stop point is a deterministic single-instrument in-memory matcher with explicit operating
modes, a safe serialized transition graph, and atomic halted-only global Mass Cancel. It remains
non-durable, single-process, caller-serialized, and has no production-ready or high-availability
claim.
