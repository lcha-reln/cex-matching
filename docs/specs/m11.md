# M11 single-member Aeron Cluster adapter

`course/m11-start` freezes PLAN v0.14 as a structured RED. M00-M10 remain the inherited executable
baseline, including the `matching-0.5.0` local-runtime stop point. M11 adds one complexity axis: put
the same deterministic, single-shard matching state machine behind a real, single-member Aeron
Cluster log, application protocol, correlated response, and Cluster snapshot lifecycle. It does not
change matching business semantics and it does not claim high availability.

The start ref contains this contract, a content-addressed `matching.m11.workload.v1` profile, six
binary compatibility goldens, and the `matching.m11.check.v1` structured RED judge. It deliberately
contains no Aeron dependency, `matching-cluster-runtime` module, `ClusteredService`, Cluster client,
snapshot implementation, completion judge, or evidence writer. The normal root build continues to
run the completed M10 judge and stays green. `./gradlew m11Check` first writes a schema-valid
`GOAL_NOT_IMPLEMENTED` report and then exits non-zero: the explicit M11 start-tag gate is
intentionally RED without making the inherited root build RED.

## Objective and only added axis

M11 must prove that one ordered command corpus produces the same canonical business events,
results, and semantic state through three complete executions:

```text
canonical request bytes -> direct adapter -> deterministic matching state machine
canonical request bytes -> fresh uninterrupted single-member Cluster -> ClusteredService -> same state machine
canonical request bytes -> second fresh Cluster -> midpoint snapshot/restart -> same state machine
```

Aeron owns Cluster-log ordering and its snapshot lifecycle. The matching state machine continues to
own order-book, rule, market-mode, STP, command-identity, result, and semantic-digest state. The
adapter may not reinterpret an Aeron publication position, session ID, timestamp, member ID, role,
or log position as business identity or business state.

`matching-core` must remain byte-identical to `course/m10-complete` and infrastructure-free. M11 may
expose the smallest internal state-machine seam required to reuse the existing M08C1 command codec
and core applier. It must not rewrite M03 matching algorithms or weaken any M08-M10 gate.

## Runtime boundary

The completion target adds one production module, `matching-cluster-runtime`, fixed to Aeron
`1.52.2`, Agrona `2.5.0`, and the repository Java 25 toolchain. Only this module may depend on Aeron.
The `ClusteredService` path must not construct or call `LocalMatchingRuntime`, `LocalMatchingService`,
`SegmentedWal`, `SnapshotStore`, or any second application WAL. The standalone M08/M09 runtime
remains an inherited executable baseline, not a second durability truth inside Cluster mode.

The real M11 service applies business commands only from `ClusteredService.onSessionMessage`. Session
open/close, role change, timer callbacks, Cluster timestamp, and runtime positions cannot mutate
business state. The service cannot call a database, HTTP endpoint, external service, or application
file store. Aeron-owned directories belong to the launcher/runtime container; application state
enters and leaves the service only through the replicated log and Cluster snapshot publication/image.

The completion harness launches a real localhost single-member Media Driver, Archive, Consensus
Module, and Clustered Service Container. Member `0` must become the appointed Leader. The harness
uses an isolated owned directory below `build/tmp/m11`, serial execution, bounded readiness and
response deadlines, and explicit Aeron error/counter capture. It must not depend on Docker, a remote
judge, an external service, fixed sleeps, or a machine-global shared directory.

## Ingress, identity, correlation, and response

Every application request carries an invocation `correlationId` outside one canonical M08C1 command
envelope. The embedded envelope's `commandId`, producer `Slot`, and payload hash remain the durable
business identity. A retry may use another correlation while preserving exactly the same command
identity. Aeron `clusterSessionId` is transport state and is never an order, command, producer, or
deduplication key.

`payloadHash` is exactly SHA-256 over the canonical M08 command-payload bytes embedded inside the
M08C1 envelope. The decoder recomputes it before apply. It never hashes the outer M11 request,
correlation, requested response version, or whole M08C1 envelope, so transport retries and response
down-encoding cannot change durable identity.

A positive `AeronCluster.offer` result means only that the ingress Publication accepted bytes. It is
not Cluster commit, service apply, or business success. A healthy M11 client waits for a decoded
application response with the same correlation. The state machine binds a new or duplicate result
before attempting `ClientSession.offer`; response publication outcome cannot roll back, repeat, or
otherwise influence business state. A healthy single-member response timeout is a harness
`SYSTEM_ERROR`, not a fabricated business rejection. The `UNKNOWN` state and retry workflow are M12
work.

The response is a bounded result commitment, not the future M14 business-output stream. It includes
correlation, outcome, optional `commandId` echo, application sequence, result/semantic digest, or a
stable rejection code. Response v2 does not echo Slot or payload hash, so that optional UUID is not
the complete durable identity. It does not inline an unbounded Mass Cancel event list. The service still
retains the full canonical result in its identity table, and the M11 judge compares normalized full
business events through a non-influencing observation seam. M14 later introduces resumable
Execution and Market streams.

## Frozen N and N-1 application compatibility

Application request, response, and snapshot formats each freeze `current=2` and
`minimumReadable=1`. These are application schemas, not Aeron's internal client, consensus, Archive,
or mark-file protocol versions.

- Request v1 contains correlation plus a canonical M08C1 envelope and always selects response v1.
- Request v2 additionally carries a requested response schema version, which must be exactly `1` or
  `2`. Any other value is a pre-apply protocol failure: zero business-state mutation and no
  fabricated business response.
- Response v1 contains correlation, outcome, application sequence, result digest, or rejection code.
- Response v2 additionally echoes optional `commandId` and semantic-state digest; it does not carry
  Slot or payload hash.
- Every valid M11 business outcome is representable in response v1. The current service accepts
  request v1 and v2 and can emit v1 for either request version; v2 is emitted only when request v2
  explicitly asks for it.
- Snapshot readers accept S1 and S2; the current writer emits S2 only. S1 already contains the
  complete, canonically ordered command identity and full original-result table needed for exact
  idempotency after restore.
- S2 changes no business-state coverage: it only adds explicit readable/writable protocol bounds
  plus integrity/validation fields for the identity table and semantic state.

Every version has an immutable binary golden. The current encoder must reproduce current goldens and
the current decoder must read the previous goldens without losing idempotency or original-result
replay. The N-1 files are contract fixtures created at
this start boundary; they were never a production deployment. Passing them does not prove that an
old server accepts v2, an old binary loads S2, a mixed-member Cluster is safe, or rollback works.

All integers are signed big-endian and every variable byte/string field is an `int32` byte length
followed by exact bytes. Requests use `M11Q`, schema version, template `1`, correlation UUID, the v2
requested-response version when present, and a canonical M08C1 envelope. Responses use `M11R`,
schema version, template `2`, correlation UUID, disposition, application sequence, result digest,
then v2 optional `commandId` echo and semantic digest. Snapshots use `M11S`, schema version,
template `3`, v2 bounds when present, and one canonical state payload; v2 then adds identity-table
and semantic-state digests. Both snapshot versions end in CRC32C followed by SHA-256.

The frozen state payload is generated by applying one real Place through
`MatchingCoreCommandApplier`. It serializes the complete M09-layout control state, complete ordered
order registry, transcript digest, semantic digest, and a non-empty identity table containing the
command ID, full Slot, the decoded M08 envelope's command-payload hash, and every field of the real
`CanonicalResult`. The testkit generator is the byte oracle; JSON summaries are never snapshot
state. Completion must implement a strict decoder/restorer for exactly this layout.

## Cluster snapshot contract

Both S1 and S2 Cluster snapshots contain the complete core state and an identity-result table:
command ID, Slot, payload hash, full canonical result, and the next application position. Entries
are encoded by original `CanonicalResult.applicationSequence`, strictly `1..N` without gaps. Restore
rejects duplicate command IDs or Slots and producer epoch/sequence discontinuity. The S1 and S2
snapshot goldens contain two bindings so ordering and continuity are observable fixtures.
It excludes standalone WAL positions and all runtime-only Aeron metadata. Encoding has explicit
size and entry bounds, canonical ordering, CRC32C, and SHA-256. Snapshot transport uses bounded
frames over the supplied snapshot Publication and a strict Image loader; format goldens are
independent of runtime fragmentation.

A present but truncated, corrupt, non-canonical, unsupported, duplicated, or discontinuous snapshot
fails startup closed. It never falls back to genesis. After restart, a duplicate returns the exact
original result, a conflict remains rejected without mutation, the next new command continues the
application sequence, and the semantic state equals the direct path.

The fixed corpus contains these 22 ordered scenarios:

```text

COMMAND_ID_CONFLICT_NO_MUTATION

DIRECT_CLUSTER_EVENTS_EQUAL
DIRECT_CLUSTER_DIGEST_EQUAL
RUNTIME_METADATA_EXCLUDED
NO_STANDALONE_WAL_WRITE
SNAPSHOT_ACCEPTANCE_AND_COMPLETION_DISTINCT
SNAPSHOT_STATE_EXACT_AFTER_RESTART
SNAPSHOT_IDENTITY_RESULT_SURVIVES
SNAPSHOT_SEQUENCE_CONTINUES
CURRENT_READS_PREVIOUS_SNAPSHOT
CURRENT_DOWN_ENCODES_PREVIOUS_RESPONSE
```

The generated differential profile uses repository-owned SplitMix64 seed `6111`: one continuous
4,096-action corpus divided into 32 ordered segments of 128 actions. The segments are not 32
fresh-state histories: application sequence and producer cursors continue across every boundary.
The fixed lane-major order is `CURRENT_NEW[0..7]`, `PREVIOUS_NEW[0..7]`,
`DUPLICATE_REPLAY[0..7]`, then `IDENTITY_CONFLICT[0..7]`. Two fresh generations must be byte-exact.
The same ordered bytes run through three complete paths: one direct adapter,
one fresh uninterrupted single-member Cluster, and a second fresh single-member Cluster that is
restarted from a midpoint snapshot. Each Cluster path therefore executes 4,096 ingress actions,
for 8,192 actual Cluster ingress actions in total. Normalized full events, result digests, and final
semantic digests must agree across all three paths; runtime metadata is recorded separately and is
never normalized into business equality.

The two Cluster executions use distinct owned roots and disjoint local port blocks. The snapshot cut
is the global corpus boundary immediately after action 2,048, not a per-segment index.

After generated action 2,048 on the restart path, the harness pauses new ingress and sends
`sendAdminRequestToTakeASnapshot`. `AdminResponseCode.OK` proves only that the management request
was accepted; it is explicitly not a completion signal. Before shutdown, a bounded completion
barrier must observe all of the following: the Aeron snapshot counter advances, the Cluster control
toggle resets to `NEUTRAL`, and new consensus-module service ID `-1` plus application service ID `0`
snapshot entries appear in the Recording Log at the same leadership term and log position with new
recording IDs. The service also records the SHA-256 of the
snapshot payload it published. Only then may the harness close client, service container, consensus
module, Archive, and driver in ownership order while preserving the Cluster and Archive directories.
On restart, `onStart` must consume a non-null snapshot Image whose payload digest and application
sequence match that completed snapshot. The harness validates restored state, identity table,
original results, and next sequence before offering the remaining suffix. Final state equality alone
cannot substitute for these completion and load witnesses because log replay could otherwise hide a
snapshot that was never completed or loaded.

All 28 proof obligations in the workload require executed witnesses. The completion judge must kill
these ten candidates as `STUDENT_FAILURE` and persist one-minimal replayable counterexamples:

```text
M11-OFFER-AS-SUCCESS
M11-SESSION-AS-IDENTITY
M11-CORRELATION-AS-IDENTITY
M11-RESPOND-BEFORE-BIND
M11-DROP-IDENTITY-FROM-SNAPSHOT
M11-CORRUPT-SNAPSHOT-TO-GENESIS
M11-REJECT-N-MINUS-ONE
M11-INCLUDE-RUNTIME-METADATA-IN-DIGEST
M11-DOUBLE-WRITE-LOCAL-WAL
M11-ACCEPT-UNSUPPORTED-VERSION
```

Thrown codec, Cluster-startup, and corrupt-harness controls remain `SYSTEM_ERROR`; they never count
as mutant kills or semantic evidence.

## Explicit exclusions and stop point

M11 excludes three-member replication, quorum, election/failover testing, follower catch-up,
fencing, failover-under-load, result `UNKNOWN`, retry orchestration, Cluster Backup/restore,
multi-shard routing, Cluster throughput qualification, reuse of M10 QOP as a Cluster number,
Counter/Rest/DB/HTTP, resumable downstream output, security/TLS, cross-region deployment, SBE
migration, and `matching-0.8.0`.

The M11 stop point is a real but single-member Aeron Cluster adapter whose healthy-path apply,
snapshot/restart, protocol compatibility fixtures, and business semantics match the direct runner.
One member cannot replicate and cannot survive its only member failing. M12 alone may add three
members, leader failure, quorum/catch-up, the same-command retry after `UNKNOWN`, epoch/fencing,
Cluster Backup, failure evidence, and the `matching-0.8.0` product stop point.
