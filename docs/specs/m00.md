# M00 executable input contract

Status at `course/m00.2-start`: **READY / GOAL_NOT_IMPLEMENTED**. Status at
`course/m00-complete`: **CODE_VERIFIED / PASS**.

M00 adds one complexity dimension: deterministic normalization and validation of a single limit-order
command. It never applies a valid command to an order book and never emits `Accepted`, `Rested`, or
`Trade`.

## Frozen input domain

The fixture envelope is `matching.m00.fixture.v1` JSON. JSON integers are read with arbitrary
precision so the fixture can express `Long.MAX_VALUE + 1` without truncation.

| Field | Business domain |
| --- | --- |
| `instrumentId` | exactly `BTC-USDT` |
| `orderId` | opaque integer in `1..Long.MAX_VALUE` |
| `side` | exactly `BUY` or `SELL` |
| `priceTicks` | integer in `1..Long.MAX_VALUE` |
| `quantityLots` | integer in `1..Long.MAX_VALUE` |

Strings are not trimmed and case is not folded. Fixture strings are at most 64 Unicode code points for
`instrumentId` and 16 for `side`; NUL, CR, and LF are rejected by the fixture boundary. Missing
fields, duplicate fields, wrong JSON types, floating-point values, and exponent notation are
`FIXTURE_SCHEMA_ERROR` system failures. They are not business `INVALID` results.

## Frozen business validation

Validation stops at the first invalid field in this order:

```text
instrumentId -> orderId -> side -> priceTicks -> quantityLots
```

The business codes are:

| Code | Field |
| --- | --- |
| `UNKNOWN_INSTRUMENT` | `instrumentId` |
| `INVALID_ORDER_ID` | `orderId` |
| `INVALID_SIDE` | `side` |
| `INVALID_PRICE` | `priceTicks` |
| `INVALID_QUANTITY` | `quantityLots` |

A result is only `VALID` or `INVALID(code, field)`. Invalid input does not partially mutate any
business state because M00 has no business state.

## Canonical history and digest contract

The completed unit will distinguish three byte sequences:

- `canonicalInputBytes`: produced for every schema-valid fixture record;
- `canonicalCommandBytes`: produced only for a `VALID` normalized command;
- `canonicalValidationBytes`: produced for every business validation result.

`canonicalHistoryBytes` uses UTF-8, LF, no BOM, the fixture array order, the field order shown below,
and shortest base-10 integers. String values use `<utf8-byte-length>:<verbatim-value>` so delimiters,
spaces, and non-ASCII input remain unambiguous. It excludes case IDs, paths, timestamps, JDK metadata,
operating-system metadata, Git metadata, and fixture expectations.

```text
M00H1|records=<n>\n
M00I1|<index>|type=PLACE_LIMIT_ORDER|instrumentId=<length>:<raw>|orderId=...|side=<length>:<raw>|priceTicks=...|quantityLots=...\n
M00C1|<index>|type=PLACE_LIMIT_ORDER|instrumentId=<length>:<normalized>|orderId=...|side=<length>:<normalized>|priceTicks=...|quantityLots=...\n
M00V1|<index>|status=VALID|code=-|field=-\n
```

Every schema-valid record contributes one `M00I1` line. A valid record then contributes one `M00C1`
line and its `M00V1` line; an invalid record omits `M00C1` and contributes
`M00V1|<index>|status=INVALID|code=<code>|field=<field>`. Every line, including the final line, ends
with LF. Indexes are zero-based shortest decimal integers. For example, `BTC-USDT` is encoded as
`8:BTC-USDT` and `BUY` as `3:BUY`.

The digest is `sha256:` followed by the 64-character lowercase SHA-256 of the exact
`canonicalHistoryBytes`. This is an internal semantic teaching format, not the M09 external wire
codec.

## Start and completion semantics

At the canonical `course/m00.2-start` ref:

- `./gradlew clean build` exits zero;
- `./gradlew m00Check` exits non-zero and writes `build/reports/m00/check.json` with
  `GOAL_NOT_IMPLEMENTED`.

The implementation branch must make `m00Check` aggregate boundary cases, error priority, checked-in
goldens, 100 deterministic replays, the core architecture boundary, and semantic mutant
`M00-QTY-ZERO-ACCEPTED`. Infrastructure or parser errors are always `SYSTEM_ERROR`; they never count
as killed mutants.

M00 is complete only after a clean-tree `m00Evidence` run and an annotated `course/m00-complete` tag.
It is not a product release and creates no `matching-*` release tag.

The completed judge uses `matching.m00.check.v2`; the v1 report at every start ref remains the
smaller `GOAL_NOT_IMPLEMENTED` contract and is not redefined. The frozen fixture produces 37 LF
terminated lines, 3199 UTF-8 bytes, and this digest:

```text
sha256:2d287d677d5f200f2b5bd1dd18dabbd40e865779489ce6da36d0411a3b670669
```

Completion artifacts are written beneath `build/reports/m00/`; clean-tree evidence is written to
`build/lab-evidence/M00/manifest.json`. Semantic reports contain no timestamp, absolute path, or
host metadata. The evidence envelope records the source commit, JDK, OS, architecture, generation
time, limitations, and verified SHA-256 for every referenced artifact.

## Superseded start refs

The immutable refs below are retained as failure evidence, not as runnable teaching baselines:

- `course/m00-start`: the custom Gradle task source was excluded by an over-broad ignore rule, so a
  clean checkout could not configure the build;
- `course/m00.1-start`: the missing source was fixed, but the checked-in documentation still named
  the failed original ref as the start boundary.

`course/m00.2-start` is the first self-contained start ref whose clean-checkout behavior and
documentation agree. No business semantics changed between the patch refs.
