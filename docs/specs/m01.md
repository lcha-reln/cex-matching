# M01 single-instrument GTC price-time contract

Status at `course/m01-start`: **READY / GOAL_NOT_IMPLEMENTED**. The intended completion ref is the
future annotated tag `course/m01-complete`.

M01 adds exactly one complexity dimension to M00: a business-valid `PlaceLimitOrder` is applied to a
stateful, single-writer order book and produces a deterministic, ordered event batch. Acceptance
sequence, price levels, FIFO queues, partial fills, multi-level execution, and resting remainder are
the necessary parts of that one state transition model. They are not separate product features.

## Frozen scope

- The only instrument is `BTC-USDT`.
- The only command is M00's `PlaceLimitOrderInput`; valid commands are normalized with the frozen
  `PlaceLimitOrderValidator`.
- Every valid command is a GTC limit order. There is no time-in-force field in M01.
- Calls are serialized by the caller. The core creates no thread, lock, clock, random source, I/O,
  network, database, or Aeron dependency.
- Accepted order IDs in one scenario are unique. Duplicate IDs and duplicate commands are outside
  the M01 scenario domain; they are not a new business rejection rule.

An invalid M00 input maps to a single `Rejected` event and does not change the order book or consume
an acceptance sequence. M01 introduces no validation code of its own.

addressable lifecycle semantics belong to M02.

## Event grammar and matching rules

An invalid batch is exactly:

```text
Rejected
```

A valid batch is exactly:

```text
Accepted, Trade*, Rested?
```

`Accepted` is always first. `Rested` exists if and only if the taker has a positive remainder and is
always last. A fully executed taker has no `Rested` event. Each resting maker produces its own
positive-quantity `Trade`; trades are never aggregated across makers.

Acceptance sequences start at 1, are strictly increasing, and are consumed only by valid commands.
A resting remainder retains its original acceptance sequence. They are in-memory time-priority
identities, not command IDs, durable log positions, or public event sequences.

- bids are ordered from higher price to lower price;
- asks are ordered from lower price to higher price;
- makers at one price execute by ascending acceptance sequence;
- a buy crosses while `buy.priceTicks >= bestAsk.priceTicks`;
- a sell crosses while `sell.priceTicks <= bestBid.priceTicks`;
- trade price is always the resting maker price;
- trade quantity is the minimum of maker and taker remaining quantity.

After every command, zero-remaining orders and empty price levels are absent. If both sides are
non-empty, `bestBid < bestAsk`; M01 never leaves a crossed book behind.

## Conservation and deterministic history

For every valid command:

```text
original taker quantity = sum(batch trade quantities) + rested remainder
maker remaining after  = maker remaining before - sum(trades for that maker)
```

All terms are non-negative and every trade quantity is positive. Testkit aggregation uses arbitrary
precision integers so several individually valid `long` quantities cannot overflow an invariant
calculation. Fully filled orders are absent from the final active book.

The strict fixture envelope is `matching.m01.scenario.v1`. Its checked-in expectations are an
independent oracle: production code must never generate or overwrite them. The completed unit will
encode fixture-order commands, ordered event batches, and book-after snapshots as UTF-8/LF/no-BOM
`M01H1` canonical history. It excludes paths, timestamps, host/JDK/Git metadata, and mutable object
identity. One hundred fresh-engine replays of the frozen corpus must produce identical batches,
snapshots, bytes, and one SHA-256 digest.

## Required scenarios and counterexamples

The frozen corpus covers:

- invalid input does not mutate state or consume sequence;
- empty and non-crossing books rest orders;
- exact touch executes at maker price;
- a later, better-priced maker beats an earlier worse-priced maker;
- three makers at one price execute FIFO;
- a maker may remain partially filled at the head of its level;
- one taker may sweep several levels and rest its remainder;
- sell-side matching mirrors buy-side matching.

The completed `m01Check` must reject all three required semantic mutants as `STUDENT_FAILURE`:

```text
M01-SAME-PRICE-LIFO
M01-TAKER-PRICE
M01-SKIP-FIRST-MAKER
```

A throwing, null, malformed, parser, or infrastructure candidate is `SYSTEM_ERROR` and never counts
as a killed mutant. The production control must pass the same independent oracle.

## Explicit exclusions

M01 does not implement cancellation, amendment, an order-ID index, terminal lifecycle states,
duplicate-command idempotency, IOC, FOK, post-only, market orders, STP, market state, price bands,
fees, accounts, assets, random property generation, shrinking, an independent reference model,
performance layout, WAL, snapshot, persistence, networking, runtime adapters, SBE, Aeron, or high
availability. It creates no new Gradle module.

M02 adds addressable cancellation and irreversible terminal states. M03 adds an independent
reference model and generated counterexamples. No capability from those units may be pulled into
M01 to make the implementation look more complete.
