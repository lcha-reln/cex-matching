# M02 addressable order lifecycle contract

`course/m02-start` freezes the **READY / GOAL_NOT_IMPLEMENTED** boundary. M02 adds exactly one
complexity dimension to the completed M01 matcher: every accepted order ID becomes a lifetime
identity that can be addressed by `CancelOrderInput` and can enter an irreversible terminal state.
The start ref contains the contract, strict oracle, and intentional failing check, but no M02
production implementation.

## Inherited boundary

- The only instrument remains `BTC-USDT`.
- `PlaceLimitOrderInput` keeps the complete M00 validation and M01 price-time semantics.
- Calls remain serialized by the caller. The core remains single-writer and creates no thread,
  lock, clock, random source, I/O, network, database, or Aeron dependency.
- Price priority, acceptance-sequence FIFO, maker-price execution, partial fills, multi-level
  execution, and immutable full-depth snapshots remain unchanged.
- M01's eight-scenario, 22-command corpus, canonical history, and evidence remain immutable
  historical contracts. M02 has its own scenario and check schemas and must not rewrite M01
  evidence.

## Frozen command and public result shape

The command union in the scenario corpus is exactly `PLACE | CANCEL`. The completed core extends
the existing engine without creating another module:

```text
CancelOrderInput(String instrumentId, BigInteger orderId)

SingleInstrumentMatchingEngine
├── ExecutionBatch place(PlaceLimitOrderInput input)
├── ExecutionBatch cancel(CancelOrderInput input)
└── OrderBookSnapshot snapshot()
```

`CancelOrderInput` is a schema-valid boundary value. Business validation uses the inherited order
`instrumentId -> orderId`. An unknown instrument produces
`Rejected(UNKNOWN_INSTRUMENT, "instrumentId")`; a value outside `1..Long.MAX_VALUE` produces
`Rejected(INVALID_ORDER_ID, "orderId")`. Invalid cancellation never reads or changes lifecycle
state and never consumes an acceptance sequence.

M02 extends the event union with these exact semantic values:

```text
PlaceRejected(OrderId orderId, PlaceRejectionCode code)
  code = DUPLICATE_ORDER_ID

CancelRejected(OrderId orderId, CancelRejectionCode code)
  code = ORDER_NOT_FOUND | ORDER_ALREADY_FILLED | ORDER_ALREADY_CANCELED

Canceled(AcceptanceSequence sequence, OrderId orderId, Side side,
         PriceTicks priceTicks, QuantityLots canceledQuantityLots)
```

The public spelling is `Canceled` / `CANCELED` with one `l`. Internal lifecycle terms are
`RESTING`, `FILLED`, and `CANCELED`; they are not added to `OrderBookSnapshot` and are not exposed as
a second public state query.

## Command-specific event grammar

Every command returns one immutable `ExecutionBatch` containing ordered events and `bookAfter`.
The legal grammars are:

```text
invalid PLACE  = Rejected
duplicate PLACE = PlaceRejected
accepted PLACE = Accepted, Trade*, Rested?

invalid CANCEL  = Rejected
unknown/terminal CANCEL = CancelRejected
active CANCEL   = Canceled
```

The inherited accepted-place grammar is unchanged. `PlaceRejected`, `CancelRejected`, and
`Canceled` are each the only event in their batch. A cancel result never emits `Accepted`, `Trade`,
or `Rested`.

## Lifetime identity and state transitions

An order ID is unused until a M00-valid place command with that ID passes the duplicate check. That
command alone consumes the next acceptance sequence and emits `Accepted`. Invalid place input does
not reserve its ID. A duplicate place emits `PlaceRejected(DUPLICATE_ORDER_ID)`, does not consume a
sequence, and cannot modify the original order.

The first accepted order permanently owns its ID for the lifetime of the engine:

```text
UNSEEN --accepted with remainder--> RESTING
UNSEEN --accepted fully executed--> FILLED
RESTING --remaining fully traded--> FILLED
RESTING --successful cancel-------> CANCELED
FILLED ----------------------------> FILLED
CANCELED --------------------------> CANCELED
```

No later place command can reuse an ID in `RESTING`, `FILLED`, or `CANCELED`. This irreversible
identity rule prevents a terminal order from reappearing even though M02 deliberately has no
command ID, request retry protocol, or durable idempotency table.

Cancellation has these deterministic outcomes:

- an ID never accepted by this engine returns `ORDER_NOT_FOUND`;
- `ORDER_NOT_FOUND` does not reserve an ID or create a terminal tombstone, so the same ID may still
  be accepted by its first later valid place command;
- a resting or partially filled order removes exactly its positive remaining quantity and emits
  `Canceled` with the original sequence, side, price, and that removed quantity;
- a fully filled order returns `ORDER_ALREADY_FILLED`;
- a canceled order, including every repeated cancel, returns `ORDER_ALREADY_CANCELED`.

Every rejected or successful cancel leaves the next acceptance sequence unchanged.

## Book, registry, and terminal invariants

The implementation must introduce exactly one authoritative, addressable lifecycle registry. It
retains every accepted order ID in `RESTING`, `FILLED`, or `CANCELED` state. Price-level nodes
reference the same internal order record; they do not own a second lifecycle state. After every
command:

- the registry's `RESTING` entries and all resting book nodes form a bijection by order ID;
- every `RESTING` entry has one positive-quantity book node at the same side and price;
- every `FILLED` or `CANCELED` entry has no book node;
- canceling the first, middle, or last order at a price removes only that order;
- the relative order of every surviving same-price maker is unchanged;
- an empty price level is removed, and the book remains ordered, non-crossed, and free of zero
  quantities;
- matching a maker to zero remaining removes its book node and records `FILLED` before
  the command completes;
- a taker is recorded as `FILLED` when it has no remainder; otherwise its single resting remainder
  is recorded as `RESTING` with its original acceptance sequence and book node.

The collection and node layout are not frozen. An `ordersById` map plus addressable queue nodes is
a reasonable implementation. Any secondary lookup must only address the same authoritative order
record: separate active and terminal stores cannot each own lifecycle truth. The oracle judges
behavior and invariants rather than a named collection.

## Frozen oracle

The strict `matching.m02.scenario.v1` document contains ten fresh-engine scenarios and 34 commands.
Every command carries its complete independent `events` and `bookAfter` expectation. The scenarios,
in order, are:

1. invalid cancel does not mutate the book or consume an acceptance sequence;
2. canceling the only resting order removes its price level;
3. canceling the middle maker preserves survivor FIFO;
4. canceling a partially filled maker removes only its remainder;
5. canceling an unknown ID has a stable result;
6. late cancels prove that both a fully filled maker and an immediately fully filled taker retain
   the filled terminal state;
7. repeated cancel reports the canceled terminal state;
8. an active duplicate ID is rejected without changing the original order;
9. a filled ID cannot be reused or resurrected;
10. a byte-for-byte repeated place for a canceled ID is still a duplicate, and the next distinct
    accepted order receives the continuous sequence.

At the start ref, `m02Check` validates the exact corpus schema, byte digest, scenario and case
identities, command counts, command union, and negative schema probes. It then writes
`build/reports/m02/check.json` with schema `matching.m02.check.v1` and exits non-zero with
`GOAL_NOT_IMPLEMENTED`. A compiler, test, parser, filesystem, or runner failure is never an
acceptable educational gap.

At `course/m02-complete`, the `matching.m02.check.v2` judge replaces the start runner, compares the
production engine against this oracle, enforces lifecycle/registry invariants, replays deterministic
`M02H1` history 100 times, and kills these required semantic mutants as `STUDENT_FAILURE`:

```text
M02-CANCEL-WRONG-FIFO-ORDER
M02-GHOST-RESTING-ORDER
M02-TERMINAL-ID-REUSE
M02-REPEATED-CANCEL-SUCCEEDS
```

Throwing or malformed candidates remain `SYSTEM_ERROR` and fail closed. The frozen canonical
history is 181 lines and 17,160 UTF-8 bytes with digest
`sha256:32054d63accba99b19db823c41f74bda73dc3b8a009b528f2834d2bc70839d16`;
100 fresh parses and fresh engines produce one distinct digest. Completion evidence is bound to
annotated `course/m02-complete`; M02 is not a product release, so `productRelease` remains `null`.
The manifest claim IDs and order are frozen as:

```text
m00-m01-regression
cancel-event-batches
addressable-order-cancellation
irreversible-terminal-states
order-registry-book-invariants
deterministic-lifecycle-history
semantic-mutants
architecture-boundary
```

Its limitation text and order are frozen as:

```text
Only one in-memory BTC-USDT GTC limit-order book with place and cancel is implemented.
Accepted order IDs are unique for the lifetime of one engine process; terminal identity records are retained without pruning.
A repeated place command is rejected as a duplicate order ID; command-level idempotency and prior-result replay are not implemented.
There is no Cancel/Replace, amendment, mass cancel, IOC, FOK, post-only, market order, STP, market state, or price band.
There is no account, asset, position, fee, settlement, reservation-release, or risk logic.
Fixed scenarios and semantic mutants are not the independent generated reference model or property proof deferred to M03.
The unit has no persistence, networking, database, threads, Aeron, or high availability.
The evidence makes no throughput, latency, recovery, durable-idempotency, or production-readiness claim.
```

## Explicit exclusions

M02 does not add command-level idempotency, a command ID, producer sequence, Cancel/Replace, batch
cancel, mass cancel, IOC, FOK, post-only, market order, STP, market state, price bands, accounts,
assets, reserved funds, fees, settlement, independent generated reference-model testing,
performance layout promises, WAL, snapshot, persistence, networking, runtime adapters, SBE, Aeron,
or high availability. Those remain later units.

The stable result of a repeated cancel follows from irreversible order lifecycle state; it is not a
claim that an arbitrary retried command executes exactly once.
