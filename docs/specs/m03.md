# M03 independent reference model and generated-property contract

`course/m03-start` freezes a **READY / GOAL_NOT_IMPLEMENTED** boundary on top of the completed M02
matcher. M03 adds exactly one complexity dimension: an independently implemented executable model
and a deterministic generated-history judge that can find, minimize, persist, and replay semantic
counterexamples. It does not change the production matching command or event surface.

## Inherited production boundary

- The production subject remains one caller-serialized, in-memory `BTC-USDT` GTC limit-order book.
- Its public commands remain exactly `PLACE | CANCEL`; its event and lifecycle semantics remain the
  completed M02 contract.
- M00 validation, M01 price-time matching, and M02 addressable cancellation are cumulative
  regressions. M03 may fix a discovered production defect, but it may not add another order type,
  instrument, service, runtime, persistence layer, thread, clock, network, database, or Aeron
  dependency.
- The completed `matching-core` remains the production subject. M03 adds one test-only
  `matching-reference` module and the corresponding judge in `matching-testkit`; it does not add a
  second production matcher or service.

## Three independent observation paths

M03 completion requires three paths with different responsibilities:

1. `M03ProductionCandidate` adapts only the public `SingleInstrumentMatchingEngine` command results
   into neutral immutable values. It contains no expected-result logic.
2. `LinearReferenceModel` lives in `matching-reference`, whose Gradle dependency graph contains no
   `matching-core` or `matching-testkit`. It validates raw inputs itself, stores accepted orders in
   one flat list, and selects a maker by a complete linear scan ordered by `(best price,
   acceptanceSequence)`. It must not import or instantiate production engine, validator, order-book,
   lifecycle, adapter, or M01/M02 oracle classes, and must not copy the production `TreeMap` plus
   per-level queue structure.
3. `M03PropertyJudge` maintains a third event-derived ledger and checks event grammar, positive
   trades, quantity partition, unique active identity, book ordering/FIFO, and an uncrossed batch
   boundary before comparing the complete production outcome with the reference outcome.

Shared infrastructure such as strict JSON parsing, hashing, atomic report writes, and neutral M03
command/result records is allowed. Sharing production transition code, validation code, collection
layout, or expected outcomes is forbidden because it would turn a common-mode defect into a false
PASS.

## Frozen generated suite

The immutable configuration is
`matching-testkit/src/test/resources/m03/fixtures/property-suite-v1.json`, validated by
`matching.m03.generator.v1`. Its UTF-8 SHA-256 is
`3e051347b9bd42aac431d02949c0c1b72daa667d10a03cc8aeb09a6b5a74d24e`.

- PRNG: repository-owned `splitmix64-v1`; no JDK random implementation, wall clock, environment,
  iteration order, or machine data may affect generation.
- Base seed: decimal `6824`.
- Suite size: exactly 256 fresh-engine histories and 64 commands per history, for 16,384 command
  boundaries.
- Each history seed is derived only from the base seed and history index. Regenerating the suite
  twice must produce identical command bytes and one digest.
- Histories are evenly stratified across four lane prefixes: `BEST_PRICE`, `SAME_PRICE_FIFO`,
  `MAKER_PRICE`, and `CANCELED_IDENTITY`; every lane owns exactly 64 histories.
- The remaining commands use the frozen 65/35 Place/Cancel weighting and bounded domains in the
  configuration. Each raw field has a deterministic 1-in-32 invalid branch. Reuse within the
  `1..32` order-ID domain deliberately produces active and terminal duplicates.
- Every generated history starts with a fresh production candidate, reference model, and event
  ledger. No generated command or state leaks into another history.

The four lane prefixes are edge-family constructors, not handwritten expected outcomes. Their
input values are frozen so every correctness category is reached deterministically; all expected
events and books are still computed independently by the reference model. Random suffixes then
compose validation, crossing, partial-fill, duplicate, cancel, and terminal paths that fixed
examples do not enumerate.

## Properties and failure classification

After every command, the judge must check in this order:

1. the candidate returned a structurally legal event batch for the generated command;
2. every trade quantity is positive and candidate events preserve per-order quantity partition;
3. the returned book has positive unique resting orders, price ordering, same-price sequence FIFO,
   no empty level, and no crossed boundary;
4. the event-derived lifecycle ledger and returned book are bijective for resting identities, while
   filled/canceled identities are absent and terminal;
5. the complete ordered event list and full-depth `bookAfter` equal the independent reference
   outcome.

A business mismatch is `STUDENT_FAILURE` and includes history identity, seed, command index,
property ID, command, expected outcome, and actual outcome. Candidate exceptions or malformed
results, generator/parser/schema errors, filesystem errors, and judge defects are `SYSTEM_ERROR`
and fail closed. A throwing control must remain `SYSTEM_ERROR`; it can never count as a killed
semantic mutant.

## Shrink, persist, and replay

For every required semantic mutant, the generated suite first finds a deterministic failing
history. A fresh-candidate predicate then preserves the same property fingerprint while applying:

1. deterministic chunk deletion (`ddmin`);
2. single-command deletion to a fixed point;
3. deterministic scalar simplification of instrument, order ID, side, price, and quantity.

The shrinker must re-run the entire retained history from fresh state after every candidate change.
It may not mutate a live failed engine or infer a smaller history from the failure text. Completion
persists the **full minimized command history**, reference outcome after every command, first actual
mismatch, seed, original length, minimized length, property fingerprint, and one-minimal check.
Saving only a seed or stack trace is insufficient.

The strict `matching.m03.counterexamples.v1` artifact contains exactly one scenario per required
mutant. A separate replay phase reads the persisted bytes through the schema boundary, creates
fresh candidates, and must reproduce the same `STUDENT_FAILURE` fingerprint for all entries. A
canonical `M03X1` byte encoding and SHA-256 bind the persisted artifact; platform paths, class
names, timestamps, Git metadata, and object `toString()` output are forbidden from the encoding.

## Required semantic mutants

The shared generated-property judge must kill these six plausible business faults:

```text
M03-BEST-PRICE-LAST
M03-SAME-PRICE-LIFO
M03-TAKER-PRICE-TRADE
M03-TRADE-QUANTITY-OVERFLOW
M03-CANCEL-GHOST-BOOK
M03-CANCELED-ID-REUSE
```

The best-price and FIFO mutants reorder otherwise plausible trades; the maker-price mutant reports
the taker limit; the quantity mutant overstates a positive trade; the cancel mutant returns the
pre-cancel book; and the terminal mutant resurrects a canceled identity. Each must first fail in
the generated suite, shrink to a non-empty strictly shorter history, persist as complete JSON, pass
the frozen one-minimal check, and fail at the same property after strict replay. The completion
report freezes the observed minimized lengths and canonical counterexample digest; those are
generated evidence, not guessed start-state constants.

## Completion reports and evidence

At the start ref, `m03Check` validates the exact generator bytes, schema, shape, lane identities,
domain, counts, and six negative schema probes. It writes
`build/reports/m03/check.json` with schema `matching.m03.check.v1`, status
`GOAL_NOT_IMPLEMENTED`, and exits non-zero. `./gradlew clean build` remains green because it runs the
completed M02 regression rather than pretending the M03 goal is complete.

At `course/m03-complete`, `matching.m03.check.v2` must prove:

- the full M00–M02 regression remains PASS;
- two fresh generations produce the same command digest;
- production and independent reference agree at all 16,384 command boundaries;
- all 16,384 event-ledger and book/lifecycle property checks pass;
- all six mutants are `STUDENT_FAILURE`, are minimized, persisted, one-minimal, and replayed;
- the throwing control is `SYSTEM_ERROR`;
- `matching-reference` has no core/testkit dependency and uses the structurally independent
  linear-scan design, while `matching-core` retains its M02 architecture boundary.

Clean-tree evidence is bound to annotated `course/m03-complete`. Because M03 is a named product
stopping point, the same commit must also carry annotated `matching-0.1.0`, and the manifest
`productRelease` must equal that tag. Claim IDs and limitation text are frozen in the completed
writer and cross-checked by CI and the course site.

## Explicit exclusions and stop point

M03 does not add command IDs, durable idempotency, Cancel/Replace, mass cancel, IOC, FOK, post-only,
market orders, STP, market state, price bands, another instrument, account/asset/position/fee/risk
logic, terminal pruning, persistence, WAL, snapshot, database, networking, threads, performance
layout, benchmarks, SBE, Aeron, or high availability.

The stop point is annotated `matching-0.1.0`: a correct and generated-property-proven single-pair
GTC limit matcher with addressable cancel, still single-process and memory-only. The bounded suite
is stronger than fixed examples but is not exhaustive formal verification, a throughput claim, a
crash-recovery claim, or production readiness.
