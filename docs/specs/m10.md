# M10 bounded admission and honest performance qualification

`course/m10-start` freezes PLAN v0.12 as a structured RED. M00–M09 remain the inherited executable
baseline. M10 adds one complexity axis to that baseline: a bounded, single-worker local admission
service plus a reproducible method for finding a machine-specific operating envelope. It does not
change the matching-core business grammar, M08C1 identity, M08W1 durability order, M09S1 recovery,
or the canonical result and transcript contracts.

The start ref contains only this contract, the content-addressed `matching.m10.workload.v1` profile,
and the `matching.m10.check.v1` RED judge. It deliberately contains no `LocalMatchingService`, JMH
benchmark, load runner, completion judge, or M10 evidence. `./gradlew m10Check` must therefore write
`GOAL_NOT_IMPLEMENTED` and exit nonzero while the inherited M09 judge and normal build stay GREEN.

## Bounded local admission

The completion target introduces a local service in front of exactly one caller-serialized
`LocalMatchingRuntime`. The service requires a positive, finite configured queue capacity; the M10
qualification profile freezes that capacity at 64. Submission is a non-blocking `trySubmit`; a full queue returns
`OVERLOADED_BEFORE_WAL` immediately. It must not wait for capacity, append to M08W1, bind command or
producer-slot identity, apply matching state, or masquerade as a durable business result.

An admitted command means only that the service has taken ownership of an immutable copy of the
canonical envelope bytes and associated completion handle. It is not an ACK. The one worker removes
admitted items in FIFO order and invokes the unchanged local runtime. Every admitted command must
eventually receive exactly one unchanged `SubmissionResult` returned by that runtime or one explicit
service failure. This includes `NewDurablyApplied`, `DuplicateReplayed`, `StructuralRejected`,
`PreflightRejected`, `CheckpointRequired`, `DurabilityUnknown`, and `FailedClosed`. There is no
silent drop, second completion, synthetic success, or alternate result grammar. Only the durable
result variants are acknowledgements; enqueue and every non-durable result remain non-ACK outcomes.

If M09 returns `CheckpointRequired` before WAL mutation, the service completes that admitted attempt
with the unchanged result. The workload coordinator may then publish a checkpoint and submit the
exact same canonical envelope as a separately reconciled retry. Command identity remains unchanged,
and the logical operation latency continues from its original scheduled arrival through the
checkpoint pause and retry. This is maintenance around the same single-worker boundary, not a
second application lane and not permission to hide the intermediate `SubmissionResult`.

An unexpected worker or runtime failure closes admission, rejects new offers, and completes every
already accepted but unfinished item with an explicit failure. It never skips the failed item and
continues as though order were preserved. A deliberate quiesce similarly rejects new offers first,
then drains every already admitted item before reporting completion. Capacity includes all queue
slots visible to admission; the implementation may not hide an unbounded handoff elsewhere.

Offer accounting must reconcile exactly:

```text
offers = admitted + overloaded + closed-or-invalid
admitted = submission-result-completions + explicit-service-failures + pending-at-observation-cut
```

At a terminal quiesced observation cut, `pending-at-observation-cut` is zero. No overload response
may appear in the submission-result completion side of the second equation. Submission-result
variant counts must sum to `submission-result-completions`; only `NewDurablyApplied` and
`DuplicateReplayed` contribute durable ACK counts.

## Microbenchmarks are diagnostic only

The micro suite uses JMH `SampleTime` to isolate exactly two diagnostics: the core
`restingMakerThenMatchingTaker` path and canonical M08 envelope decoding. Its raw configuration and
complete per-fork histograms may diagnose regressions, allocation, or a suspicious hot path, but no micro result gates
the product release. M10 never combines a JMH operation score with local-runtime throughput and
never presents a microbenchmark as an end-to-end capacity claim.

## Qualification runtime is explicit, finite, and not the M09 default

M09 keeps its production default recovery bound of 64 suffix records and 1 MiB. A continuously
growing identity-result table plus an M09S1 full snapshot at every 64 records cannot honestly sustain
the 1,800-second unique-command qualification stream: repeated full snapshots create quadratic write
amplification and eventually reach the 256-MiB snapshot-format bound. M10 does not hide this conflict,
weaken durable identity, or silently call a tuned run the M09 default.

The machine-specific M10 qualification policy is frozen as `M10Q1`: a finite 1,000,000-record / 1-GiB
recovery suffix budget, a 1,024-byte planning ceiling for this exact workload, and one proactive
checkpoint scheduled 100,000,000 nanoseconds after every phase begins and admitted within another
10,000,000 nanoseconds. The checkpoint enters the same bounded owner-worker FIFO as business work,
so its pause remains in scheduled-arrival latency. The runner fails before a phase unless two
independent bounds fit: the existing suffix plus arrivals scheduled before that 110,000,000-nanosecond
admission deadline plus the queue-and-owner occupancy bound must fit before the checkpoint; every
planned durable arrival plus the same conservative queue-and-owner bound must fit after it.
The runner must not add both sides together as if no checkpoint existed. It also fails during
execution if any durable record exceeds the planning ceiling. Every report publishes
both `M10Q1` and the unchanged M09 default. A capacity envelope from `M10Q1` is valid only for that
recorded recovery tradeoff; it is never evidence for the 64-record default.

Fresh reopen uses the same finite `M10Q1` budget and records actual suffix records, suffix bytes, and
monotonic recovery time. A separate ordered fresh-apply diagnostic uses the M08 no-snapshot runtime
only to compare the canonical result/state transcript without performing a second series of M09 full
snapshots. It does not replace the finite-budget recovery proof.

## Release open-loop workload

The release profile generates arrivals on a dedicated thread independently of completions,
checkpoint coordination, resource collection, and JSON/gzip artifact I/O. Every operation has a planned
arrival time. End-to-end latency starts at that scheduled arrival, not when the producer eventually
gets CPU time and not at the actual `trySubmit` call. This retains scheduler delay, queue delay,
checkpoint pauses, WAL force, apply, and completion delivery instead of hiding them through
coordinated omission.

The observation boundary remains the immutable scheduled window end. The producer is not interrupted
at that boundary: it receives at most 250,000,000 nanoseconds of closure grace to materialize exactly
one initial admission decision for every planned arrival. Producer lag is measured from scheduled
arrival to the real admission-gate decision; p99 may not exceed 50,000,000 nanoseconds and maximum
lag may not exceed 250,000,000 nanoseconds. A missing decision or either lag violation is a
system/method failure, not saturation and not a slower capacity result. The completion/checkpoint
coordinator may fall behind and expose real queueing, but it cannot stop the initial scheduled-arrival
thread or turn open-loop traffic into a completion-paced loop.

At the scheduled cut, a planned arrival whose admission decision has not happened is explicit demand
backlog. Cut attempt accounting contains only real admission decisions before the cut; it never
invents offers for that backlog. Queue-depth percentiles at the cut likewise use only those exact gate
decisions. Later decisions may add overload, saturation, or method failure, but neither producer
closure nor terminal drain may recompute the cut to improve it. Raw admission evidence uses
`admissionDecisionNanos` with `ADMISSION_GATE_DECISION`; durable completion uses
`ownerCompletedNanos` with `OWNER_COMPLETED_UNDER_GATE`.

The frozen release method is:

1. Run one unpaced 20-second calibration solely to choose the reference rate. Calibration output is
   not a release latency sample and cannot itself pass qualification.
2. Run three complete sweeps. Each rate receives 10 seconds of warmup followed by 30 seconds of
   measured traffic.
3. In every sweep, visit the reference-rate permille ladder in this exact order:
   `250, 500, 700, 850, 1000, 1150, 1350, 1600`.
4. Persist raw samples and publish p50, p95, p99, and p99.9 using quantiles
   `0.5, 0.95, 0.99, 0.999`. The judge independently recomputes each published quantile from the raw
   sample multiset and frozen rank rule.

An arrival that the service rejects as overloaded remains an explicit workload outcome; it is not
dropped from the denominator or converted into a zero-latency sample. Offered, admitted,
overloaded, closed, every `SubmissionResult` variant, explicit-service-failure, and terminal-pending
totals must all reconcile.

## Saturation, knee, and qualified operating point

A measured rate first freezes an observation cut at the scheduled window end. Its ending backlog is
the sum of planned arrivals still awaiting an admission decision and admitted logical work still
awaiting a durable terminal result. It is saturated when any one of these conditions is true at that
cut:

- overload rejection count is greater than zero;
- p99 queue depth is at least 80% of the capacity;
- completed/admitted is below 99.5%; or
- terminal backlog growth is greater than 10% of the capacity.

Only after this cut does the runner drain every accepted logical operation to a zero-pending terminal
cut and perform recovery/correctness checks. That terminal drain cannot retroactively erase backlog
or improve completed/admitted at the scheduled observation cut.

The per-sweep knee is the first member of the first pair of consecutive saturated rates. If a sweep
has no such pair, qualification fails instead of inventing a knee beyond the ladder. The published
knee is the minimum of all three sweep knees. The method first computes the candidate
`floor(70% * published-knee)`, then selects as `QOP` the highest measured ladder rate at or below that
candidate which was unsaturated in every sweep. If no such measured rate exists, qualification fails;
it never labels an already saturated point as qualified. A release report must also retain the
candidate, selected QOP, and above-knee measurements with their explicit overload or saturation
evidence; publishing only the comfortable side of the curve is invalid.

M10 makes no portable minimum orders-per-second promise. Calibration, the knee, and QOP are valid
only with the exact source, workload, JVM flags, operating system, CPU, memory, storage, filesystem,
power policy, and run timestamps recorded in that evidence set.

## Resource and soak evidence

Every measured rate records raw latency and queue observations together with allocation, GC, CPU,
memory, and queue-depth dimensions. A dedicated sampler covers scheduled-window start through the
terminal drain at a one-second target cadence and a two-second maximum scheduled gap. Cumulative
allocation, GC, and CPU counters must be monotonic; memory and queue gauges must be non-negative but
are not mislabelled as cumulative. A missing dimension is a failed qualification, not a zero. Unit
and collection mechanism must be explicit; an unavailable collector is reported as a system or
environment failure.

After selecting QOP, the release profile runs a 1,800-second soak at that offered load. Its scheduled
observation cut must itself remain unsaturated; otherwise the runner drains and verifies recovery but
must not write a release `PASS`. The soak must retain
the same open-loop arrival origin, reconciliation, correctness, resource, and fail-closed rules. The
finite soak can reveal drift, backlog growth, GC pathologies, leaks, and recovery mismatch on the
recorded machine. It is not proof of a universal SLA or indefinite stability.

## CI smoke is not release evidence

`CI_SMOKE` is method-isomorphic but deliberately short: one-second calibration, one sweep, one-second
warmup and two-second measurement per rate, plus a three-second soak. It uses the same ladder,
scheduled-arrival origin, percentiles, reconciliation, saturation rules, and correctness checks.
Its result scope is exactly `METHOD_SMOKE_ONLY`, and `eligibleForReleaseEvidence` is frozen to
`false`.

Ordinary `m10Check` and shared GitHub CI may execute only this short profile. A PASS there can prove
that the method, schemas, accounting, and semantic guards execute; it cannot populate release
throughput, latency, knee, QOP, or soak claims. The eventual `matching-0.5.0` evidence must come from
the full release profile and must identify the environment that actually ran it.

## Correctness remains a hard gate

Performance never disables inherited correctness. Every admitted command must pass through the
exact M09 `SubmissionResult`; durable variants must also preserve the canonical result, transcript,
and terminal state. Structural, preflight, checkpoint-required, durability-unknown, and fail-closed
variants must not be upgraded to an ACK. Every overload rejection must be absent from WAL, identity,
and matching state. After measured load and a clean close, a fresh runtime recovered from the
published snapshot plus WAL suffix must produce the exact canonical state and result digest.

The generated admission model uses repository-owned SplitMix64 seed `6010`: 64 histories by 256
actions, for 16,384 generated actions. Four equal modulo lanes cover `BELOW_CAPACITY`, `QUEUE_FULL`,
`CHECKPOINT_PAUSE`, and `FAIL_CLOSE_RETRY`. Two fresh generations must be byte-exact. A throwing
harness, unavailable collector, malformed sample, timeout, arithmetic failure, or recovery crash is
`SYSTEM_ERROR`; it never becomes PASS and never counts as a mutant kill.

## Evidence and release boundary

The completion report must bind the workload-profile hash, source commit, environment fingerprint,
JVM flags, fixed and generated results, raw arrivals and completions, raw latency samples, raw queue
samples, exact `(point, logical operation, attempt)` joins, reconstructed accepted-trace hash,
observation and terminal cuts, producer-lag gates, the explicit M09-default/M10Q1 recovery boundary,
percentile reconciliation, resource series, both JMH diagnostic histograms, all three sweep knees, published knee, QOP,
above-knee outcomes, the 1,800-second soak, load-then-recovery equality, mutant results, and
counterexamples. Summary JSON without the bound raw artifacts is insufficient.

Clean-tree evidence is eligible only when annotated `course/m10-complete` and annotated
`matching-0.5.0` both peel to the exact source commit. The release writer must recheck clean source,
tag identity, every artifact hash, and report schema before and after atomic publication.

## Explicit exclusions and stopping point

M10 excludes Aeron, Cluster, Raft, replication, leader election, quorum, failover, Cluster Backup,
remote clients, multiple shards, shard routing, group commit, concurrent snapshot, cross-region
tests, database synchronization, gateway/API behavior, market data, and absolute portable capacity
claims. It does not call a local single-process queue highly available.

The stopping point is one bounded local admission service, one worker, one M09 local runtime, and a
machine-qualified performance envelope. This is the last local-runtime release boundary before the
M11 single-node Aeron Cluster adapter is introduced. The finite corpus, generated histories,
microbenchmarks, open-loop sweeps, and 30-minute soak are strong executable evidence for their exact
inputs and environment; they are not exhaustive exploration, formal verification, physical-media
durability proof, or a universal production SLA.
