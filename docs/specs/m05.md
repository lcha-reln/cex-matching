# M05 versioned order-entry price-band contract

`course/m05-start` freezes the **READY / GOAL_NOT_IMPLEMENTED** boundary on top of
`course/m04-complete`; `course/m05-complete` is the **CODE_VERIFIED / PASS** target described by
this contract. M05 adds one complexity dimension only: an immutable, versioned order-entry price
band can be prepared and activated at a deterministic serialized matcher boundary. The lifecycle is
the delivery mechanism for that one rule. Market operating modes and Mass Cancel are split into
M06; STP and later units move back by one slot.

## Inherited boundary

- The only instrument remains `BTC-USDT`, and every order remains a protected limit order.
- M00 field validation, M01 price-time priority, M02 addressable lifecycle, M03 independent model,
  and M04 `GTC/IOC/FOK/POST_ONLY` semantics remain authoritative.
- The M04 five-field input, policy request, public legacy entrypoints, acceptance sequence,
  command canonical bytes, M04F1/M04H1/M04X1 digests, and `matching-0.1.0` tag are not rewritten.
- The default engine bootstraps rule version `0`, content-addressed unbounded entry band
  `[1, Long.MAX_VALUE]`. Therefore every M04 Place observes the same business decision as before.
- Calls remain caller-serialized. `matching-core` still creates no thread, clock, random source,
  file, network, database, or Aeron dependency.
- M05 is an evidence-only course unit. It does not create a new `matching-*` product release.

## One new rule axis

The authoritative artifact is an absolute tick interval, not a floating percentage calculation:

```text
MarketRuleSetArtifact(
  schemaVersion = "matching.market-rule-set.v1",
  instrumentId = "BTC-USDT",
  RuleSetVersion version,
  PriceTicks lowerInclusive,
  PriceTicks upperInclusive,
  String contentHash
)

RuleSetIdentity(version, contentHash)
```

`0 <= version <= Long.MAX_VALUE`, both bounds are positive signed `long` ticks, and
`lowerInclusive <= upperInclusive`. The artifact owns neither a market-data source nor a rounding
formula. A future control plane may compile a reference price and percentage policy into these
exact bounds, but those external inputs are outside M05.

`contentHash` is lowercase `sha256:<64 hex>` over repository-owned `M05RS1` canonical UTF-8 bytes.
Prepare recomputes it; the claimed hash is never trusted. The exact text is LF-delimited and ends in
one LF:

```text
M05RS1
schemaVersion=matching.market-rule-set.v1
instrumentId=BTC-USDT
version=<canonical decimal>
lowerInclusive=<canonical decimal>
upperInclusive=<canonical decimal>
```

There is no locale, whitespace normalization, map traversal, wall clock, or platform line ending.

The engine exposes these new boundaries:

```text
MarketControlBatch prepareRuleSet(PrepareRuleSet command)
MarketControlBatch activateRuleSet(ActivateRuleSet command)
ExecutionBatch placeGoverned(GovernedPlaceLimitOrderRequest request)
MarketControlSnapshot marketControlSnapshot()
```

The inherited `place`, `placeRequest`, `cancel`, and `snapshot` methods remain callable. They still
obey the active band; `placeGoverned` additionally fails closed when the caller's expected
`RuleSetIdentity` is stale.

## Prepare lifecycle

Prepare is a state-machine command, not a node-local cache refresh.

1. The command carries the complete artifact and the exact expected active identity.
2. Expected-active mismatch, malformed content hash, hash mismatch, non-increasing version, or
   same-version/different-content conflict is rejected without changing active, prepared, book,
   order registry, or acceptance sequence.
3. The first valid higher version occupies the single prepared slot.
4. Repeating the exact same prepared identity is idempotent and reports `ALREADY_PREPARED`.
5. A higher valid version may supersede the prepared slot; an older prepared candidate cannot.
6. Prepare never changes order admission and never makes the artifact active.

The active identity is immutable until a successful Activate. A failed command cannot leave a
partially copied artifact or a new identity paired with old bounds.

## Activate and execution fence

Activate carries the target prepared identity and exact expected active identity. It succeeds only
when both identities match current state and the prepared artifact still recomputes to its claimed
hash. On success it atomically:

```text
active := prepared
prepared := empty
controlRevision := controlRevision + 1
activationFence := (
  appliedCommandSequence,
  controlRevision,
  firstAcceptanceSequence = nextAcceptanceSequence
)
```

Every core command that returns a deterministic business/control result consumes one positive,
monotonic in-memory `ApplicationSequence`, including business and control rejection. Null calls,
schema construction failures, and `SYSTEM_ERROR` consume none. Activate carries its expected
application sequence and succeeds only at that exact boundary; the first later command is `S + 1`.
The successful Activate method boundary is therefore the serialized execution fence. Every command
completed before it observes the old artifact; every later Place observes the new artifact.
`firstAcceptanceSequence` does not order rejected commands or Cancel. It proves the accepted-order
cut: historical accepted orders below it were admitted by an older rule, while any newly accepted
order at or above it must carry the new admission identity. M07 will make the command history
durable; M05 does not pretend that the in-memory application sequence is a WAL or Cluster log
position.

Sequence exhaustion is detected before domain mutation. A rejected Activate still consumes its
declared application boundary but preserves the old active artifact and prepared slot so an operator
can inspect state and retry at the next exact boundary.

## Governed Place decision priority

M05 inserts two checks without moving the inherited M04 decisions that precede them:

```text
1. M00_FIELD_VALIDATION
2. EXECUTION_POLICY_VALIDATION
3. DUPLICATE_ORDER_ID
4. EXPECTED_ACTIVE_RULE_SET
5. ACTIVE_ORDER_ENTRY_PRICE_BAND
6. POLICY_STATE_PRECHECK
7. ACCEPTANCE_SEQUENCE_CAPACITY
8. ACCEPT_AND_EXECUTE
```

Consequences are contractual:

- malformed fields or policy win before every state-dependent observation;
- duplicate identity wins before stale-fence or band inspection, preserving M04 identity priority;
- a stale expected identity returns `PlaceRejected(RULE_SET_MISMATCH)`;
- a valid price below or above the inclusive active band returns
  `PlaceRejected(PRICE_OUTSIDE_ACTIVE_BAND)`;
- both rejections are singleton, reserve no identity, consume no acceptance sequence, execute no
  maker, and leave book and market-control state unchanged;
- FOK and Post-only inspect liquidity only after the order has passed the venue band;
- both BUY and SELL use the same inclusive entry interval; touch at either bound is valid.

The per-order M04 `priceTicks` and M05 price band answer different questions. The first protects the
order's worst execution price. The second decides whether the venue admits that limit price at all.
Passing the venue band never weakens maker-price execution or the order's limit protection.

## Grandfathered resting orders and attribution

Activation never scans, reprices, reorders, or cancels the existing book. A resting maker outside a
new band remains live at its original price-time priority and may trade at its maker price. The band
is deliberately an **order-entry** rule, not a continuous-validity or execution-price band.

Every accepted order stores its admission `RuleSetIdentity`. Every `Accepted`, `Rested`, `Trade`,
`RemainderCanceled`, successful `Canceled`, and resting-order snapshot exposes enough identity data
to recover maker admission, taker admission, and the active execution identity. Every returned batch
also carries its active rule identity and control revision. Compatibility constructors normalize
older M00-M04 values to the version-0 bootstrap identity; M04 business projections deliberately
ignore the added attribution and must keep their exact historical canonical digests.

M05 does not provide a hidden revalidation flag. Clearing or halting a market is a separate control
state machine and enters M06 together with deterministic operator Mass Cancel.

## Deterministic proof inputs

The fixed input corpus is
`matching-testkit/src/test/resources/m05/fixtures/versioned-price-band-v1.json`, schema
`matching.m05.scenario.v1`. It covers legacy bootstrap, hash and version conflict, idempotent
Prepare, Activate target and expected-active mismatch, serialized fence, stale governed Place,
inclusive lower/upper ticks, both out-of-band directions, decision priority, all four M04 policies,
and cross-version grandfathered makers.

The generated profile is
`matching-testkit/src/test/resources/m05/fixtures/property-suite-v1.json`, schema
`matching.m05.generator.v1`:

- repository-owned `splitmix64-v1` with decimal base seed `5505`;
- 160 fresh histories, 64 commands each, 10,240 command boundaries;
- five lanes, 32 histories each: lifecycle/hash, activation fence, inclusive band, grandfathered
  maker, and mixed M04 policy/lifecycle;
- generated expected outcomes come only from the independent flat-list M05 reference model;
- a third event/state ledger derives order lifecycle, acceptance sequence, active/prepared identity,
  activation fences, and book state without trusting production snapshots.

Completion freezes an M05 fixed result history and an M05 generated command history. Their byte
counts, line counts, and SHA-256 values are discovered once by the completed implementation, then
made exact in the completion tag; no start artifact invents output values.

## Required semantic mutants

The completion judge must kill these exact eight faults as `STUDENT_FAILURE`:

```text
M05-HASH-MISMATCH-PREPARED
M05-SAME-VERSION-DIFFERENT-HASH-ACCEPTED
M05-ACTIVATE-WITHOUT-PREPARE
M05-STALE-ACTIVATION-FENCE-ACCEPTED
M05-FAILED-ACTIVATION-CHANGES-ACTIVE
M05-OUT-OF-BAND-PLACE-ACCEPTED
M05-STALE-PLACE-RULE-ACCEPTED
M05-ACTIVATION-REVALIDATES-RESTING
```

Each counterexample starts from a fresh engine, is deterministically shrunk, is one-minimal,
persists the complete history, and replays to the same property fingerprint. A throwing candidate,
reference, generator, parser, shrinker, or filesystem control is `SYSTEM_ERROR`, never a mutant
kill.

## Start, completion, evidence, and stopping point

At `course/m05-start`, `./gradlew clean build --no-daemon` proves M04 remains PASS, while
`./gradlew m05Check --no-daemon` validates this contract and both frozen inputs, writes strict
schema `matching.m05.check.v1`, reports `GOAL_NOT_IMPLEMENTED`, and exits non-zero intentionally.

At `course/m05-complete`, the same command writes strict `matching.m05.check.v2` with PASS only if:

- the production and independent reference implementations agree at every fixed and generated
  boundary;
- all control, price-band, attribution, book, sequence, and quantity invariants pass;
- the exact M04 completion proof and historical digests remain unchanged;
- all eight mutants have one-minimal replayable counterexamples and the throwing control remains
  `SYSTEM_ERROR`;
- the architecture gate still rejects I/O, time, randomness, concurrency, Aeron, and production
  dependency on reference/testkit.

`m05Evidence` runs only from a clean tree whose annotated `course/m05-complete` peels to HEAD. The
manifest binds source commit, frozen inputs, exact reports, claims, and limitations. It records
`productRelease: null` and makes no persistence, performance, recovery, networking, or high
availability claim.

The M05 stop point is a deterministic single-instrument matcher with content-addressed,
versioned, atomic order-entry price-band activation and historical rule attribution. It still has no
operating mode, Mass Cancel, STP, WAL, snapshot recovery, network protocol, Aeron, replication, or
high-availability guarantee.
