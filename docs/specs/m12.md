# M12 three-member Leader-failure correctness

`course/m12-start` freezes PLAN v0.15 as an intentional structured RED. M00-M11 remain the
executable baseline. M12 adds exactly one complexity axis: replace the M11 single-member topology
with one static three-member Aeron Cluster and prove that losing the current Leader does not create
two business effects for one durable command identity. The completion ref preserves that start
artifact byte-for-byte and separately records the automatic-election correction described below.

This unit is not a generic distributed-systems demo and it does not claim that the matcher is fully
production-qualified. It is a single-shard correctness release. Capacity, backup, disk or host
loss, network-partition matrices, rolling upgrade, multi-shard routing, Counter, REST, databases,
and external side effects remain outside M12.

## The success boundary

M11 already separates ingress Publication acceptance from a correlated application response. M12
makes the consequence explicit under failure:

```text
not accepted by ingress                 -> NOT_SUBMITTED
accepted, but no trusted response seen  -> UNKNOWN
correlated response from current client -> ACKNOWLEDGED
```

`NOT_SUBMITTED`, `UNKNOWN`, and `ACKNOWLEDGED` are client invocation states. They are not matching
outcomes and are not added to the M11 request, response, or snapshot codecs. A timeout after a
successful `AeronCluster.offer` must never be converted into a rejection. A caller may resolve an
`UNKNOWN` only by retrying the same canonical M08 command identity—command ID, producer Slot, and
payload hash—with a fresh invocation correlation.

If the first invocation committed, the retry returns `DUPLICATE_REPLAYED` with the original
application sequence and result digest. If it did not commit, the retry may return `NEW_APPLIED`.
Both cases converge to one bound result and one business effect. Retrying with a new command ID or
Slot is a different command and is forbidden as an unknown-outcome recovery strategy.

## Three-member topology and ownership

The completion target launches three real Aeron `ClusteredMediaDriver` plus
`ClusteredServiceContainer` pairs with static member IDs `0`, `1`, and `2`. Every member owns a
different Aeron, Archive, and Cluster directory and a disjoint five-port UDP endpoint block. One
client owns a fourth Aeron directory. All three members use Aeron's automatic-election value
`appointedLeaderId=-1`; both the initial Leader and every replacement Leader are observations from
the real run rather than application-selected identities.

### Completion-time correction to the frozen start contract

The immutable start workload named `realClusterProfile.appointedInitialLeaderId=0`. Implementing
the real failure path exposed that this cannot be mapped to Aeron's `appointedLeaderId(0)` while
retaining high availability: a non-null appointed Leader disables automated elections, so the two
survivors remain unable to elect a replacement after member `0` exits.

M12 does not hide that design error by rewriting `course/m12-start`, changing the frozen workload
SHA, configuring different election modes on different members, or deleting the failed run. The
completion report publishes `matching.m12.contract-correction.v1`: the frozen field and value stay
visible, the effective Aeron value is `-1`, `automaticElection=true`, and `initialLeaderId` records
whichever static member the real election chose. Correctness assertions require exactly one initial
Leader, a different live replacement, and a higher term; they do not require member `0` or `1` to
win an automatic election.

All members run the M11 deterministic state machine, request/response codecs, and snapshot codec.
Those business and durable-wire boundaries remain byte-identical. M12 does make one explicit
transport-adapter correction in `M11ClusteredMatchingService`: once a business result is committed,
persistent egress failure is recorded as an undelivered-response diagnostic rather than thrown back
through the replicated service callback. Dedicated behavior tests cover bounded backpressure,
terminal publications, closing sessions, component failure, and same-identity replay after an
undelivered result. There is no application WAL, database, HTTP call, or service-local recovery
authority. `matching-core` and all six M11 application Golden files remain byte-identical to
`course/m11-complete`.

The fault controller lives outside `ClusteredService`: it observes the current topology and forcibly
terminates the selected member process. The service never kills itself and cannot choose the fault
schedule. Every voting member runs in a distinct child JVM with its own PID, components,
directories, ports, diagnostics, and lifecycle handle. All three child JVMs still share one local
machine, so M12 does not claim host or disk isolation.

## Frozen fault schedule

The repository-owned workload uses SplitMix64 seed `6120` and a fixed phase order:

1. Start members `0,1,2`; observe exactly one Leader and two Followers.
2. Submit 32 new commands and observe correlated acknowledgements.
3. Retry eight acknowledged identities and require exact original-result replay.
4. Offer one command, withhold response observation, wait until the replicated services applied it,
   abandon that invocation as `UNKNOWN`, and kill the current Leader from the external controller.
5. Observe a new Leader, a higher leadership term, and a client connection to that Leader. Retry the
   same unknown identity and require the original result with no second effect.
6. Submit 32 new commands after failover and retry eight of them.
7. Restart the former Leader from its preserved Aeron-owned state. Require it to join as Follower and
   catch up to identical application sequence, identity table, and semantic digest.
8. Stop both Followers, leaving the current Leader without a majority. Offer one command and require
   `UNKNOWN`, never an acknowledgement. Restore one Follower and retry the same identity; whether the
   pending offer committed or the retry first commits it, the final history must contain one effect.
9. Restore the final member and require all three state images to converge.

The controller uses bounded polling plus component-error capture. Fixed sleeps, remote judges,
Docker, and external services are not permitted. Election duration, term values, log positions, and
member chosen as the second Leader are observations, not hard-coded business expectations.
Every topology or convergence decision requires two fresh observations from the same PIDs with no
observed intervening authority or state change: each `statusSequence` advances while role,
closed-election state, leadership term, log and business state stay unchanged inside a monotonic
freshness bound. Immediately before each kill the
controller rechecks that stable witness against the live child PID and records that exact pre-stop
authority. A preserved member is not restarted after a guessed sleep: the parent maps that member's
Aeron 1.52.2 `ArchiveMarkFile`, repeatedly reads `activityTimestampVolatile()`, and permits
`freshStart=false` only after the observed activity age is strictly greater than the dependency's
10,000 ms liveness timeout. The three successful restart predicates, stopped PIDs, mark-file paths,
timestamps, ages, probe counts, and monotonic wait durations are independently schema-bound.
Expected Aeron fail-stop diagnostics are allowlisted to leader-heartbeat timeout,
inactive-follower quorum, and the numeric quorum-position-backwards warning, with at most one of
each family per member-process lifetime; any other, repeated-family, or dropped warning classifies
the run as `SYSTEM_ERROR`. The replicated attempt-42 pre-fault witness must contain no warnings.

## Authority boundary

Leadership term, leader member ID, cluster session ID, timestamp, and log position are transport
authority evidence. They may guide the client to the current Leader, but they never enter durable
command identity, result digests, snapshots, or semantic matching state. The connected Aeron client
must observe a new term/Leader before accepting a post-failure response. A restarted former Leader
must be a Follower while the replacement remains Leader.

The real fail-stop schedule records that all post-failure acknowledgements are accepted under the
replacement client generation and its observed replacement-Leader authority; the comparison uses
the latest stable authority immediately before the kill, not the initial startup term. History calls
these fields `responseAcceptedUnderCurrentClientAuthority` and
`observedResponseAuthorityTerm`: neither field claims to identify the server-side term in which an
effect was applied. A unit-level invocation-state test and a semantic mutant exercise rejection of
mismatched client authority. Because the M11 response wire does not itself carry cryptographic
Leader/term provenance and M12 does not inject delayed old egress, this is not a general delayed-
response fencing proof. It also says nothing about fencing an external database or downstream
system; those side effects do not exist in this unit.

## Deterministic judge and evidence

`./gradlew m12Check --no-daemon --max-workers=1` must execute the real fault schedule and write a
strict `matching.m12.check.v2` report. It compares every acknowledged or converged command with the
direct M11 runtime, verifies one identity-result binding per distinct command, and proves all three
members end with the same state image.

The completion judge has 14 fixed scenarios, 25 coverage obligations, eight semantic mutant models,
and three system-error controls. A system or harness error can never count as a mutant kill or a
semantic pass. `./gradlew m12Evidence` reruns the judge on a clean annotated completion/product-tag
commit and writes a content-addressed `cex.lab-evidence.v2` directory.

The release refs are:

- `contract/m12-revision` and annotated `course/m12-start` at the structured RED contract commit;
- `unit/m12`, annotated `course/m12-complete`, and annotated `matching-0.8.0` at one clean completion
  commit;
- `main` fast-forwarded to that same completion commit.

`matching-0.8.0` means “single-shard, three-member Leader-failure correctness stop point.” It is not
a latency, throughput, RTO, backup, security, cross-region, or operational-readiness qualification.

## Explicit exclusions

- Cluster Backup/restore, disk loss, host loss, and cross-region disaster recovery;
- arbitrary partitions, asymmetric delay, clock faults, and a complete split-brain matrix;
- open-loop load, TPS, percentiles, failover-under-load, RTO, and SLO claims;
- rolling or mixed-version upgrade, N-2 migration, and rollback;
- multiple shards, shard movement, instruments beyond the fixed single-shard corpus;
- Counter/REST/database integration, settlement, and external exactly-once side effects;
- resumable business-output streams, which remain an M14 concern.
