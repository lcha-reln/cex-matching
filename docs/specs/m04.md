# M04 execution-policy contract

`course/m04-start` freezes a **READY / GOAL_NOT_IMPLEMENTED** boundary on top of the published
`matching-0.1.0` matcher. M04 adds exactly one complexity dimension: one closed
`ExecutionPolicy` changes admission and remainder disposition for the existing protected limit
order. It does not add another order type, price source, participant identity, RuleSet, service, or
runtime.

## Inherited boundary

- The only instrument remains `BTC-USDT`.
- The original five-field `PlaceLimitOrderInput(instrumentId, orderId, side, priceTicks,
  quantityLots)` is immutable. Its validation order, normalization, M00 canonical bytes, and all
  M01–M03 GTC outcomes remain byte-for-byte regressions.
- The existing `place(PlaceLimitOrderInput)` method remains the legacy GTC entrypoint.
- Price-time priority, maker-price execution, partial fills, addressable cancel, irreversible order
  identity, full-depth snapshots, and the independent linear reference model remain authoritative.
- Calls remain caller-serialized. `matching-core` still creates no thread, clock, random source,
  I/O, network, database, or Aeron dependency.
- The M03 profile remains frozen at 256 histories by 64 commands and retains its exact command
  digest. Historical M03 evidence remains bound to `course/m03-complete` and
  `matching-0.1.0`; it is never regenerated against an M04 commit.

## One new request axis

The completed core adds these public semantic types without changing the five-field input:

```text
ExecutionPolicy = GTC | IOC | FOK | POST_ONLY

PlaceLimitOrderRequest(
  PlaceLimitOrderInput orderInput,
  String executionPolicy
)

SingleInstrumentMatchingEngine
├── ExecutionBatch place(PlaceLimitOrderInput input)              // exact GTC compatibility
├── ExecutionBatch placeRequest(PlaceLimitOrderRequest request)   // M04 policy boundary
├── ExecutionBatch cancel(CancelOrderInput input)
└── OrderBookSnapshot snapshot()
```

`PlaceLimitOrderRequest` is schema-valid but its raw policy string is not yet business-valid. Only
the four exact uppercase spellings above are accepted; strings are not trimmed or case-folded.
Unknown policy never defaults to GTC. The single-argument `PlaceLimitOrderRequest(orderInput)`
constructor and the legacy `place(PlaceLimitOrderInput)` method both map explicitly to GTC.
The M04 entrypoint is deliberately named `placeRequest`, rather than overloading `place`, so an
existing source call such as `engine.place(null)` does not become ambiguous.

`priceTicks` is already the user's protected execution boundary: a BUY never trades above it and a
SELL never trades below it. Therefore an aggressive IOC is an IOC limit order with an aggressive
`priceTicks`; M04 does not add a redundant `worstPriceTicks` field or an unprotected market order.

## Frozen decision priority

Every Place request is decided in this order:

```text
1. M00_FIELD_VALIDATION
2. EXECUTION_POLICY_VALIDATION
3. DUPLICATE_ORDER_ID
4. POLICY_STATE_PRECHECK
5. ACCEPTANCE_SEQUENCE_CAPACITY
6. ACCEPT_AND_EXECUTE
```

Consequences are part of the contract:

- an M00-invalid order returns the inherited `Rejected` even if its policy is also unknown;
- an otherwise valid unknown policy returns
  `Rejected(INVALID_EXECUTION_POLICY, "executionPolicy")`;
- duplicate identity wins before FOK or Post-only inspects the book;
- unknown-policy, FOK-insufficient, and Post-only rejection do not reserve an order ID, consume an
  acceptance sequence, change any maker quantity or lifecycle, or change the book;
- a later valid request may therefore be the first accepted owner of an ID rejected only by policy;
- acceptance-sequence exhaustion is checked only after every non-accepting decision has completed.

## Policy semantics

| Policy | Admission | Matching | Positive remainder | Accepted terminal state |
| --- | --- | --- | --- | --- |
| `GTC` | no policy precheck | inherited price-time matcher | rests at its limit | `RESTING` or `FILLED` |
| `IOC` | no state-dependent precheck | consumes every currently executable maker within `priceTicks` | canceled in the same batch; never rests | `CANCELED` or `FILLED` |
| `FOK` | read-only proof that the full quantity is executable within `priceTicks` | executes only after the proof succeeds | impossible | `FILLED` |
| `POST_ONLY` | rejects if the order would touch or cross the current best opposite price | never trades when accepted | full quantity rests | `RESTING` |

The policy set is intentionally one mutually exclusive enum for this Profile. M04 does not claim
that every exchange models Post-only as a time-in-force value.

### IOC remainder

An accepted IOC consumes an order ID and acceptance sequence even if it executes zero quantity.
Any positive remainder emits one final explicit event:

```text
RemainderCanceled(
  AcceptanceSequence sequence,
  OrderId orderId,
  Side side,
  PriceTicks priceTicks,
  QuantityLots canceledQuantityLots,
  RemainderCancelReason reason = IOC_REMAINDER
)
```

The implementation must never publish `Rested` and then silently remove the order. The accepted IOC
is permanently `FILLED` or `CANCELED`; a later Place with the same ID is a duplicate, and Cancel of
an IOC remainder reports the inherited canceled terminal result.

Quantity partition becomes:

```text
original = filled + resting + userCanceled + policyRemainderCanceled
```

All terms are non-negative, and only one positive non-filled disposition can exist at a command
boundary.

### FOK atomicity

FOK atomicity means all-or-none inside one serialized matcher command. Preflight is a read-only
scan of all executable makers in price-time order and stops as soon as the remaining need reaches
zero. It subtracts from a remaining need rather than summing `long` liquidity, so a deep book cannot
overflow an accumulator.

Insufficient FOK returns `PlaceRejected(FOK_NOT_FILLABLE)` as a singleton batch. No maker,
lifecycle, book node, order identity, sequence, or event may change. A sufficient FOK then runs the
normal matcher and must finish fully filled. Liquidity beyond the request's `priceTicks` never
counts, even if the total book would otherwise be sufficient.

### Post-only admission

Post-only is rejected when its limit **touches or crosses** the best opposite price:

```text
BUY  rejects when priceTicks >= bestAsk
SELL rejects when priceTicks <= bestBid
```

The rejection is `PlaceRejected(POST_ONLY_WOULD_TAKE)` and has zero business side effect. An empty
or non-crossing book accepts the request, consumes identity and sequence, emits exactly
`Accepted, Rested`, and appends the full quantity at the normal FIFO tail. M04 does not auto-adjust
the limit or convert the request to another policy.

## Event grammar

The complete grammar is:

```text
invalid M00 input                  = Rejected
unknown policy                    = Rejected(INVALID_EXECUTION_POLICY, "executionPolicy")
duplicate identity                = PlaceRejected(DUPLICATE_ORDER_ID)
FOK insufficient                  = PlaceRejected(FOK_NOT_FILLABLE)
POST_ONLY touches or crosses      = PlaceRejected(POST_ONLY_WOULD_TAKE)

accepted GTC                      = Accepted, Trade*, Rested?
accepted IOC                      = Accepted, Trade*, RemainderCanceled?
accepted FOK                      = Accepted, Trade+
accepted POST_ONLY                = Accepted, Rested

invalid CANCEL                    = Rejected
unknown or terminal CANCEL        = CancelRejected
active CANCEL                     = Canceled
```

`Accepted` carries the normalized `ExecutionPolicy`; its five-argument compatibility constructor
still means GTC. `PlaceRejected` is reserved for a normalized command rejected before acceptance:
duplicate identity, FOK insufficiency, or Post-only taking liquidity. Raw policy failure remains a
field `Rejected` and never reaches those state-dependent checks.

`RemainderCanceled` is final, belongs to the accepted taker, and equals the exact positive quantity
left after its trades. A fully filled IOC has no remainder event. Accepted FOK has at least one
trade because quantities are positive. Accepted Post-only has no trade.

## Frozen deterministic proof inputs

The fixed input corpus is
`matching-testkit/src/test/resources/m04/fixtures/execution-policy-v1.json`, schema
`matching.m04.scenario.v1`. Its SHA-256 is
`a8bf834828847a24d316bf6f760d008809901d8e3e2ff132276225b0aa79f596`.

It contains 14 fresh-engine scenarios and 48 commands: 44 Place and four Cancel. Place policy
counts are 25 GTC, five IOC, six FOK, six Post-only, and two deliberately unknown policies. It
covers legacy GTC, validation priority, IOC zero/partial/full execution, protected price limits,
FOK insufficiency/exact/multi-level execution, Post-only empty/non-cross/touch/cross behavior,
identity and sequence continuity, and BUY/SELL symmetry.

The generated profile is
`matching-testkit/src/test/resources/m04/fixtures/property-suite-v1.json`, schema
`matching.m04.generator.v1`. Its SHA-256 is
`33a24417d56b565fe9b25868e70c1faa1637a7997d92486c5d6f30113e00575d`.

- PRNG: repository-owned `splitmix64-v1`;
- base seed: decimal `4404`;
- 192 fresh histories, 64 commands per history, 12,288 command boundaries;
- six lanes, 32 histories per lane:
  `LEGACY_GTC`, `IOC_ZERO_PARTIAL_FULL`, `FOK_INSUFFICIENT_EXACT_MULTI_LEVEL`,
  `POST_ONLY_EMPTY_NON_CROSS_TOUCH_CROSS`, `IDENTITY_AND_SEQUENCE_AFTER_REJECTION`, and
  `MIXED_POLICY_CANCEL_DUPLICATE`;
- random suffix: 70/30 Place/Cancel, exact GTC/IOC/FOK/Post-only weights 35/25/20/20, unknown policy
  1-in-16 and inherited invalid-field branch 1-in-32;
- generated coverage must show both sides plus every required IOC, FOK, Post-only, identity, and
  sequence family declared in the profile.

The profile freezes inputs and coverage obligations, not expected production values. Completion
extends the independent flat-list linear reference model and the event-derived ledger; production
must not generate its own oracle.

## Required semantic mutants

The M04 generated judge must kill these exact eight business faults as `STUDENT_FAILURE`:

```text
M04-IOC-REMAINDER-RESTS
M04-IOC-BEHAVES-LIKE-FOK
M04-FOK-PARTIAL-STATE-LEAK
M04-FOK-BEST-LEVEL-ONLY
M04-FOK-IGNORES-LIMIT-PRICE
M04-POST-ONLY-TOUCH-ACCEPTED
M04-POLICY-REJECT-CONSUMES-IDENTITY
M04-UNKNOWN-POLICY-DEFAULTS-GTC
```

Every mutant must be found deterministically, shrunk from fresh state, persisted as a complete
history, checked one-minimal, parsed through the strict counterexample schema, and replayed to the
same property fingerprint. Candidate, reference, generator, parser, shrinker, or filesystem
exceptions are `SYSTEM_ERROR`; a throwing control must remain `SYSTEM_ERROR` and never count as a
killed mutant.

## Start, completion, CI, and evidence

At `course/m04-start`:

- `./gradlew clean build --no-daemon` remains green on the completed M03 boundary;
- `./gradlew m04Check --no-daemon` validates both frozen inputs, their schemas, negative probes,
  exact counts and identities, runs the completed M03 proof, writes
  `build/reports/m04/check.json` with schema `matching.m04.check.v1`, status
  `GOAL_NOT_IMPLEMENTED`, and exits non-zero;
- `PlaceLimitOrderRequest`, `ExecutionPolicy`, new policy events, policy reference behavior, M04
  generator, M04 judge, mutants, counterexamples, and evidence do not yet exist in production.

At completion, the root build changes to the completed `m04Check`. The v2 report must preserve the
exact M03 regression, compare all fixed and 12,288 generated M04 boundaries through production,
independent reference, and event ledger, prove policy-specific invariants, kill and replay all eight
mutants, and retain the dependency-free deterministic architecture.

Clean-tree evidence will bind only annotated `course/m04-complete`. M04 is not a named product
release, so `productRelease` is `null`; `matching-0.1.0` remains the earlier M03 stop and no new
`matching-*` tag is created.

## Explicit exclusions

M04 does not add an unprotected market order, a second worst-price field, GTD/DAY, Cancel/Replace,
Mass Cancel, price bands, RuleSet activation, market state, STP, participant/account identity,
assets, positions, fees, risk, settlement, command IDs, durable idempotency, terminal pruning, WAL,
snapshot, persistence, database, networking, threads, performance claims, SBE, Aeron, replication,
or high availability.

Price bands enter M05 with versioned market rules. STP enters M06 only after its interaction with
FOK and Post-only is separately contracted.
